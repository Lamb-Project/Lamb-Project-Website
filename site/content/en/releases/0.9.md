## LTI 1.3 for course activities {#lti-13}

**What it is.** The LAMB activity tool, the one a teacher adds to a course to create a chat, file-evaluation or LLM-access activity, now accepts LTI 1.3 launches as well as LTI 1.1. The same launch address serves both. Grades from file-evaluation activities return to the LMS gradebook through the LTI 1.3 grade service (Assignment and Grade Services, score scope).

**Why.** LTI 1.1 signs each launch with a secret shared between the LMS and the tool. LTI 1.3 replaces the shared secret with a sign-in exchange and signed messages that LAMB verifies against the keys the LMS publishes. Many institutions now ask for 1.3 on new integrations. LAMB adds it where course work and grades are involved, and leaves the other entry paths alone so that existing course links keep working ([issue #551](https://github.com/Lamb-Project/lamb/issues/551)).

**How it works.**

1. The system administrator opens **Admin → LTI Settings** in LAMB. The page shows the three addresses to enter in the LMS: the sign-in address, the launch address and the address of LAMB's public keys.
2. In the LMS, the administrator configures an LTI 1.3 tool with those addresses. In Moodle this is a manually configured External tool with "Keyset URL" as the public key type.
3. Back in LAMB, the administrator registers the platform with the values the LMS shows: issuer, client ID, the LMS's own sign-in, token and key addresses, and the deployment ID. The registration also says which LAMB organizations may use it and which addresses may receive grades.
4. A teacher adds the activity to a course and opens it. On the first launch the teacher links a LAMB Creator account by signing in to it once. From then on the teacher's launches open the activity setup or the instructor view, and students' launches open the activity.

Demonstration data." details="/en/releases/0.9/#screenshots" >}}

**What to know.**

- **An LMS identity does not open an organization by itself.** A teacher who arrives through LTI 1.3 must link a Creator account that the registration allows. The same email address on both sides grants nothing.
- **Public HTTPS addresses are required.** Set `LAMB_PUBLIC_BASE_URL`, and `OWI_PUBLIC_BASE_URL` when the student chat runs on a different address. LAMB keeps its signing keys in a directory that must survive restarts (`LTI13_KEY_DIR`, by default inside the data directory). Rotating the key keeps the previous public key published for 24 hours.
- **Registration is manual.** Dynamic registration, content selection (deep linking) and roster access are not part of this release.
- **Grade return uses the grade column the LMS provides** for the activity. LAMB does not create gradebook columns. With LTI 1.1 grades keep returning through the older Outcomes service.
- **The other entry paths stay on LTI 1.1:** individual-assistant publication and Creator access from the LMS are unchanged.
- **Tested with** an unmodified Moodle 4.5 and an LTI test platform, with synthetic courses and accounts. Other LMS products follow the same standard but have not been tested by the project. The implementation is not certified by 1EdTech.
- No Moodle plugin and no Moodle-side code are involved, as with every LAMB integration.

## Prompt filters: a different scenario for each conversation {#prompt-filters}

**What it is.** An assistant's system prompt can now contain values that LAMB fills in when a conversation starts. The filter that ships with 0.9 draws random whole numbers: write `{{RANDOM:25-70}}` in the system prompt and each new conversation gets its own number between 25 and 70. The numbers stay the same for the whole of that conversation.

**Why.** Teachers who use role-play asked for it. An assistant that plays a client to interview, a patient or a case to analyse gives every student the same case if the prompt is fixed, and answers travel fast between students. Drawing the values on every message does not work either: the client would change age in the middle of the interview. The filter runs once, at the start, and LAMB remembers the result ([issue #553](https://github.com/Lamb-Project/lamb/issues/553)).

**How to use it.**

1. Open the assistant's **Edit** tab and switch on **Advanced Mode**.
2. Write the markers in the system prompt, for example: `you have {{RANDOM:3-12}} employees and a budget of {{RANDOM:25-70}} thousand euros`.
3. In **Prompt filters**, choose **Add random integers**.
4. Choose **Preview sample** to see one possible result. A preview calls no model and changes nothing.
5. Save the assistant.

{{< capture src="/images/releases/0.9/prompt-filters.png" alt="Assistant editor in Advanced Mode with the Prompt filters panel: one Random integers filter and a sample of the system prompt with the numbers filled in" caption="A role-play assistant with three random values. The sample on the right shows one possible draw. LAMB 0.9, demonstration data." details="/en/releases/0.9/#screenshots" >}}

**What to know.**

- A change to the prompt or to the filters applies to **new conversations**. Conversations already started keep the values they drew.
- Filters work on the **system prompt only**. They never touch the student's messages, the retrieved course material or the prompt template.
- Without Advanced Mode the editor only shows that filters are active on the assistant. It does not remove them.
- The numbers come from the server's secure random source and are not predictable, but they are not secret either: the assistant may say them if asked. Tell the assistant in the prompt how to treat them.
- The list is built to hold other filter types later. In 0.9 the random-integer filter is the only one.
- The same settings are available from the [command line](#cli) and to LAMB LEGATUS.

## One system prompt per conversation {#prompt-lifecycle}

**What it is.** LAMB now settles an assistant's system prompt once, when a conversation starts, stores it with that conversation and reuses it on every later turn. This applies to every assistant, with or without filters. Retrieval of course material and the prompt template still run on every message.

**Why.** Prompt filters need it: a value drawn at the start has to stay put. It also removes an old surprise. In earlier versions, editing an assistant's instructions changed the behaviour of conversations already in progress from their next message on. From 0.9, an edit applies to conversations that start afterwards ([issue #555](https://github.com/Lamb-Project/lamb/issues/555)).

**What changes for teachers.** After editing an assistant's instructions, start a new chat to see the change. Test runs always start from the current instructions.

**What changes for developers.** Programs that call LAMB's OpenAI-compatible completion address keep working for single questions. For a multi-turn conversation, a program can let LAMB keep the conversation (create one with `POST /v1/conversations` and pass its `id` as `conversation_id`) or hold the settled prompt itself (ask for it with `return_prompt_context` and send it back on later turns). The repository documents both in `backend/lamb/completions/README.md`.

**What a system prompt is not.** It shapes how an assistant teaches. It is not an access control and not a place for secrets: an assistant can be talked into repeating its instructions. Work that is graded runs in the [file-evaluation activity](/en/releases/0.8/#file-evaluation), where the assistant's proposal goes to the teacher before any grade reaches the LMS.

## LAMB LEGATUS Auto mode {#legatus-auto}

**What it is.** LAMB LEGATUS, the agent that helps a teacher build and check assistants, can now carry a whole task through. Ask for "five tests for this assistant, run them, look at the failures and save a report" and it prepares one plan, asks for one approval and does the work, showing its progress as it goes.

**Why.** In 0.8 LAMB LEGATUS asked before nearly every step and closed each answer with a menu of options. That was safe, and slow: a teacher had to supervise each command of a task they had already asked for. Auto keeps the two approvals that matter and drops the rest.

**When it asks.** Two things need the teacher's approval, and one plan can cover both:

- **A change to something stored:** creating or editing an assistant or a knowledge base, saving tests, runs, evaluations or reports.
- **More than ten calls to the assistant under test** within one task, because those calls use the organization's model budget.

Reading, inspecting and answering a question need no approval. A simple question gets a direct answer.

{{< capture src="/images/releases/0.9/legatus-plan-approval.png" alt="LAMB LEGATUS panel in Auto mode showing a plan for a full activity audit, its estimated tool uses and assistant calls, and the buttons Approve, Edit proposal and Cancel" caption="One plan, one approval. Nothing has run yet. The line under the mode selector counts calls to the assistant against the allowance. LAMB 0.9, demonstration data, local model." details="/en/releases/0.9/#screenshots" >}}

**What else is new.**

- **A mode selector on each conversation:** Auto or Guided. New conversations start in Auto. Conversations from before the upgrade stay in Guided until the teacher switches them.
- **A counter** shows calls to the assistant against the allowance (ten unless a plan asked for more) and the number of tool uses. **New task** resets it when the teacher moves on to something different. The agent cannot reset its own allowance.
- **Show me.** When the work ends, a button opens the result: the report, the assistant or the test run. It opens only when clicked, checks the teacher's access again at that moment and will not navigate away from unsaved edits.

{{< capture src="/images/releases/0.9/legatus-auto-tests.png" alt="Tests tab of an assistant with three test cases and three runs marked Good, Good and Mixed as LEGATUS evaluations, beside the LAMB LEGATUS panel showing 3 of 10 assistant calls, the Changes button, the saved test report with a Show me button and the approved plan" caption="One request, one approval: LAMB LEGATUS created three tests, ran them and evaluated the answers. The verdicts are labelled as its own. The counter shows 3 of the 10 calls allowed. LAMB 0.9, demonstration data, local model." details="/en/releases/0.9/#screenshots" >}}

- **Changes.** Edits LAMB LEGATUS makes to an assistant are kept with the previous values. The teacher can inspect them and restore an earlier version. Restoring needs its own approval, and LAMB refuses it when someone has edited the assistant in the meantime.
- **Names are forgiving.** "prova carles", "Prova_Carles" and "prova-carles" find the same assistant when only one matches. When several match, LAMB LEGATUS asks which.
- **Its evaluations are labelled as its own.** A verdict LAMB LEGATUS gives on a test run is recorded as an agent evaluation, not as confirmed by the teacher.

**What to know.** Auto mode does not widen what LAMB LEGATUS may do. The organization's settings still decide which tools it has, and operations that were forbidden stay forbidden. How well it plans depends on the model the organization has chosen for it. A plan is a proposal: read it before approving.

## Assistant activity analysis {#activity-analysis}

**What it is.** A teacher can ask LAMB LEGATUS how an assistant is being used. It reads the saved conversations, looks at them along the dimensions the teacher chooses and saves a dated report in a new **Activity analysis** tab on the assistant. The tab keeps every report, newest first.

**Why.** The Activity tab already listed conversations one by one. Nobody reads two hundred transcripts to learn that half the class confuses the same two ideas, or that the assistant gives a wrong answer to a common question. The analysis is feedback for the teacher about the group and about the assistant ([issue #557](https://github.com/Lamb-Project/lamb/issues/557)).

**How to use it.**

1. Open the assistant and choose the **Activity analysis** tab.
2. Choose **Full audit** for all six dimensions, or **New analysis** to pick some: participation, usage patterns, conceptual understanding, assistant performance, friction and sentiment, and attempts to redirect the assistant.
3. If a learning scenario describes the course and what students are meant to do, LAMB LEGATUS uses it to judge what it reads. Without one it offers a general analysis and says what it cannot conclude.
4. Approve the plan. The report is saved and listed in the tab.

{{< capture src="/images/releases/0.9/activity-analysis.png" alt="Activity analysis tab of an assistant with a saved full audit: period, dimensions, the learning scenario used, a data coverage box with the number of conversations available and reviewed, and the findings" caption="A saved report. The coverage box is written by LAMB, not by the model: it states how many conversations existed, how many were provided and how many the report declares as reviewed. LAMB 0.9, synthetic conversations, local model." details="/en/releases/0.9/#screenshots" >}}

**What to know.**

- **It is about the cohort and the assistant, not a grade for anyone.** The reports are not designed to assess individual students and should not be used for that.
- **It reads a sample and says so.** By default the 20 most recent conversations, 50 at most, with limits on the length of each. Every report states how many conversations existed, how many were provided, and whether any could not be loaded or were shortened. A "full audit" means all dimensions, not every conversation ever held.
- **Only people who may read the conversations may read the reports.** Access is checked when a report or its evidence is opened, not only when it was written. An administrator limited to aggregate figures cannot open report text.
- **Reports are records.** A saved report is not rewritten. A new analysis makes a new report, and each keeps the learning scenario as it was that day.
- **Conversation text is treated as evidence.** Instructions a student wrote in a chat are something to report, not something LAMB LEGATUS obeys. An analysis makes no call to the assistant being analysed.
- **The findings come from a language model.** They can be wrong. Each one points to the conversations that support it: open them before acting on a finding.

## LLM access: faster worker {#llm-access}

[LLM access](/en/releases/0.8/#llm-access) arrived in 0.8. In 0.9 the worker that keeps students' keys in step with the teacher's rules was reworked for large courses:

- It looks only at keys of activities that are open. A round with nothing to change, on an installation with tens of thousands of issued keys, now takes milliseconds.
- **Block, Unblock, Open now and Close now take effect at once.** They no longer wait for the worker's next round.
- The intervals are settings: `TOKEN_DEALER_RECONCILE_SECONDS` (30 by default), `TOKEN_DEALER_INGEST_SECONDS` (60) and `TOKEN_DEALER_INGEST_OVERLAP_SECONDS` (600). Usage figures can be up to about a minute and a half behind. Limits do not depend on that delay: the gateway applies them itself.

## Command line {#cli}

The LAMB CLI follows the new features. Update it together with the server.

```sh
# Prompt filters
lamb assistant update 42 --system-prompt 'Client age: {{RANDOM:25-70}}' --random-filter
lamb assistant preview-filters 42
lamb assistant update 42 --no-random-filter

# LAMB LEGATUS
lamb aac mode SESSION auto        # or guided
lamb aac new-task SESSION
lamb aac report SESSION REPORT    # a saved report, no model call
lamb aac changes SESSION          # the kept history of edits
```

`lamb chat` keeps a conversation's settled prompt between messages. `--no-persist` makes each call a fresh one.

## Fixes and smaller changes {#fixes}

- **Conversation list in the Activity tab.** Paging through an assistant's conversations skipped some after the first page when student chats and the teacher's own test chats were mixed, and the teacher's chats were capped at 100. Both are fixed ([issue #558](https://github.com/Lamb-Project/lamb/issues/558)).
- **Library Manager off by default.** The optional library service is now switched off unless the installation enables it, so a default installation does not show a menu that leads nowhere.
- **Public addresses in the browser.** The container start-up now keeps the browser configuration in step with the deployment's settings. An installation behind a proxy no longer shows `localhost` in the LTI 1.1 launch address.
- **LAMB LEGATUS evidence.** When a result is too long to show in one piece, reports now say that text was shortened instead of presenting it as complete.
- **LAMB and the student chat under simultaneous use.** Earlier builds of the candidate could stop answering when students chatted while others entered an activity or teachers signed in. LAMB's calls to the student chat now have a time limit and no longer hold up other requests.

## Upgrade notes for administrators {#upgrade-notes}

- **Back up first.** Starting 0.9 on a 0.7 database applies migrations 28, 31, 33, 34 and 35. They add tables and columns and delete nothing. They cannot be undone by going back to an older version: to go back, restore the backup.
- **Conversations in progress.** A conversation that already has answers from before the upgrade has no stored prompt. In the candidate, its next message is refused and the user has to start a new conversation. The student chat shows the refusal as a generic connection error, not as an explanation. The history stays readable. Upgrade between teaching sessions and tell teachers and students in advance.
- **Student chat settings.** In the candidate, two options of the bundled student chat (Open WebUI) do not work with assistants: temporary chats, and a personal system prompt set by the student. Both end in an error message for the student. Switch off both permissions in the student chat's administration until a later version handles them.
- **File-evaluation submissions move into the data volume.** 0.9 stores submitted files under `uploads/file-eval/` in the LAMB data directory (the `lamb-data` volume), next to the database, so one backup of that volume carries both. 0.8 wrote them inside the container at `/app/backend/uploads/file-eval/`, outside the data volumes. If your installation used file evaluation on 0.8 or on an earlier 0.9 candidate, copy that directory into the data directory before you replace the container. No database change is needed ([issue #559](https://github.com/Lamb-Project/lamb/issues/559)). The command is in the [installation guide](https://github.com/Lamb-Project/lamb/blob/dev/Documentation/installation/deployLocal.md).
- **Word documents in file evaluation.** `.docx` submissions can be evaluated, like PDF and plain text. The older `.doc` format is refused at upload with a message asking for `.docx` ([issue #561](https://github.com/Lamb-Project/lamb/issues/561)).
- **New settings.** `LAMB_PUBLIC_BASE_URL` and `OWI_PUBLIC_BASE_URL` for public addresses; `LTI13_KEY_DIR` and the optional `LTI13_CA_BUNDLE` for LTI 1.3; the three `TOKEN_DEALER_*_SECONDS` intervals for the LLM access worker; and the optional `OWI_HTTP_TIMEOUT_SECONDS`, the time limit for LAMB's own calls to the student chat (10 seconds by default).
- **LTI 1.3 keys are data.** The key directory must be on storage that survives a restart and belongs in the backup. If the keys are lost, every LMS registered against them needs LAMB's new public keys before launches work again.
- **Nothing to do for LTI 1.1.** Existing consumer keys, secrets and course links are untouched.
